# Lean v1 — the commitment (implementation)

Builds on [M1](./M1.md) toward the README's **Lean v1** — *"the v1 commitment"*.

> **Build:** per-tenant **Coolify-managed Postgres** + injected `DATABASE_URL` ·
> whole-app allow-list per app · secrets store · cron · per-tenant LLM key ·
> egress-deny + outbound allowlist · **native Coolify scheduled backups** ·
> Kiosk logs/health + Uptime-Kuma + disk alert · owner field + catalog.
>
> **Done when:** Pilot 1 (Leaderboard) runs on-platform self-served; an
> unauthorized user is denied; a restore-from-backup drill passes; egress to a
> non-allowlisted host is blocked.

Everything hangs off the two M1 seams (route through Traefik+auth; every app is
an image from a Dockerfile), so v1 is purely additive.

## Provisioning saga (v1)

`orchestrator._run` extends M1 with, after build+verify:

```
build → verify → provision per-tenant DB (Coolify Postgres resource + native
backup) → regenerate egress allowlist → build env bundle (DATABASE_URL +
secrets + HTTPS_PROXY + LLM key) →
deploy on the internal tenant network behind: strip-auth → company Google
(forwardauth) → per-app allow-list (appauthz) → record + audit
```

## Network model (default-deny egress)

```
proxy      : traefik + auth + kiosk         (externally published)
tenant     : apps + their Coolify databases + litellm   internal:true  ← no egress
egress     : egress-proxy only              (the only route out)
backplane  : kiosk + postgres + litellm + registry   internal:true
```

Tenant apps live ONLY on `tenant` (internal) — so they have **no route to the
internet at all**. The single way out is the squid `egress-proxy`, which allows
only allowlisted domains; an app is given `HTTPS_PROXY` only once it has ≥1
allowlisted domain. Each app's DB is a Coolify-managed Postgres on the tenant
network (its `internal_db_url`); LLM is reachable via litellm on `tenant`. The
kiosk's own metadata Postgres is on `backplane` only, unreachable by tenants.

## Auth (v1): two forward-auth hops

1. `forwardauth` — company Google (oauth2-proxy) / dev stub: **authN** + company
   domain.
2. `appauthz` — kiosk `/internal/authz`: **authZ**, the whole-app allow-list
   (owner always; `all-staff` → any company user; else listed emails).
   Fail-closed: any gap → 403.

## Verified live

Run against a real Docker daemon (dev auth, `KIOSK_LLM_MODE=stub`). All four
done-when criteria pass:

> **Note (engine + DB swap):** the run below was captured on the original
> plain-Docker + shared-cluster build. The DB and backup paths are now
> Coolify-managed (per-tenant Coolify Postgres resource + native scheduled
> backup) and, like the rest of the Coolify port, are validated against Coolify's
> REST contract + the no-infra/db-backed test suite (`test_deploy_backends.py`,
> `test_deploy_flow.py`) rather than a live Coolify run — the live re-run is the
> EC2 `make parity` item. The auth/egress/cron done-whens are engine-independent
> and still hold as recorded.

- **Self-served app with DB + cron.** A Pilot-shaped app went drop → build →
  verify → **per-tenant DB provisioned** → deploy → live, with `DATABASE_URL`
  injected. (Now: `provision_db` asks Coolify to create a per-app Postgres
  resource, reads back its `internal_db_url`, and injects that.) A `* * * * *`
  cron job ran as a Coolify Scheduled Task (`last_ok=t`, audit `cron.run ok:true`).
- **Unauthorized user denied.** Owner → 200; a company non-owner (invite-only) →
  **403**; a non-company account → **403**; adding the non-owner to the
  allow-list → 200.
- **Restore-from-backup drill passes.** Now owned by Coolify: each tenant DB has
  a native scheduled backup with retention, and restores run from the Coolify
  dashboard (Database → Backups → execution → restore). The kiosk no longer runs
  its own `pg_dump`/restore-drill; `provision_db._finish` configures the backup
  and `test_ensure_tenant_db_creates_reuses_and_backs_up` covers that it does.
- **Egress to a non-allowlisted host is blocked.** With no allowlist the app has
  no proxy and name resolution fails (fully denied). After allowlisting
  `example.com`: `www.google.com` → squid **403 Forbidden** (denied);
  `example.com` → tunnel established (allowed). Secret injection confirmed in the
  same redeploy (`greeting=hello-from-secret`).

Exercised in `stub`/best-effort here (need external keys/services): actual LLM
Dockerfile generation (M1) and the per-tenant **LiteLLM virtual key** (skips
cleanly when LiteLLM key management isn't running). The realistic Pilot sample
[`samples/leaderboard`](./samples/leaderboard) (Flask + psycopg) builds on a
normal box; the sandbox used a zero-dependency stand-in because tenant-build pip
egress is blocked there (same limitation noted in M1).

The allow-list bypass check above (spoofing `X-App-Slug` + `X-Forwarded-Host`
while routing to `secret`) was re-run over the **committed docker-label routing
path** (Traefik v3.6) and still returns 403 — the router's server-set
`X-App-Slug` wins and the kiosk never trusts a forwardable header.

### Traefik + Docker Engine ≥ 29 (resolved)

Earlier runs needed a file-provider workaround because Traefik ≤ v3.5 pinned
Docker API 1.24 (rejected by Docker 29's 1.40 floor). Pinning `traefik:v3.6`
fixes it — the committed compose routes via container labels on Docker 29.3.1
with no workaround.
