# Create PR

Standardized workflow for creating and maintaining high-quality, reviewer-friendly Pull Requests.

## Inputs

- **Mode**: `create` (default) or `refresh`
- **PR number / URL / branch** (optional for `refresh`): if omitted, use the PR for the current branch

## Body ownership model

PR bodies managed by this skill have two ownership zones:

1. **Human-owned** — manually edited, never auto-rewritten by refresh mode:
   - `## Original Intent`
   - any narrative sections outside the managed block, including Mermaid diagrams
2. **Machine-owned** — generated by `create-pr` and safe to refresh:
   - content inside the managed block delimited by:
     - `<!-- create-pr:managed:start -->`
     - `<!-- create-pr:managed:end -->`

Refresh mode rewrites only the machine-owned block. Everything else is preserved verbatim.

## Prerequisites

- **Required:** `git` (run inside a repo), `gh` (GitHub CLI, authenticated), `jq`.
- **Optional:** a JS runner — `npx` (bundled with Node) or `bun` — enables the token-usage footer; safely skipped if absent.

## Workflow

When the user asks to "create a PR", "open a PR", or uses the `/zeus:create-pr` command, follow this workflow.

### 0. Preflight & bootstrap

```bash
PF=$(bash ${CLAUDE_SKILL_DIR}/scripts/preflight.sh) || true
printf '%s\n' "$PF" | jq -r .report   # printf, NOT echo (echo corrupts the JSON under zsh)
```

On `.ok == false`, present the `.remediation[]` fixes and re-check with `preflight.sh --fix`; proceed only at `ok: true`. Full flow (the `--fix` auto-install vs interactive steps like `gh auth login`): **`zeus/lib/PREFLIGHT.md`**.

### 1. Gather current branch context

Use the helper script instead of staged-only git diff commands:

```bash
bash ${CLAUDE_SKILL_DIR}/scripts/pr-context.sh create
```

This returns JSON with:
- detected base branch
- current branch diff range
- changed files
- diff stat
- commit history
- changed areas
- dirty worktree status
- existing PR data if the branch already has a PR

**Important:**
- The PR body must reflect the committed branch diff against the detected base branch, not only `git diff --cached`.
- Keep `git status` / dirty-worktree information as a warning to the user, not as the source of truth for the PR description.
- If `commits` is empty (no commits on the branch vs base), there is nothing to open a PR from — commit the branch's work first, then re-run `pr-context.sh`, rather than proceeding.

### 1b. Look up the linked issue (optional)

If the branch was initialized via `/zeus:propose`, a per-worktree `journey.json` records the issue number/URL. Check for it:

```bash
ISSUE_NUMBER=$(bash ${CLAUDE_SKILL_DIR}/scripts/journey.sh issue-number 2>/dev/null || true)
```

If `$ISSUE_NUMBER` is non-empty, `/zeus:create-pr` pre-fills three slots from the issue body (see step 2). If it's empty, every seeding step is a no-op and the PR is composed exactly as it is today — independence is preserved.

Also check whether an investigation is active in this worktree (written by `/zeus:investigate`):

```bash
INVESTIGATION_EPIC=$(bash ${CLAUDE_SKILL_DIR}/scripts/journey.sh investigation-epic 2>/dev/null || true)
```

If `$INVESTIGATION_EPIC` is non-empty, pass `--label investigation` to `post-pr.sh` (step 3) so the PR self-files under the investigation, and consider noting "Part of investigation #$INVESTIGATION_EPIC" in the body. If empty (the common case), this is a no-op — `/zeus:create-pr` is unchanged and needs no `/zeus:investigate`.

### 1c. Pre-PR review backstop (optional)

Don't open a PR on un-reviewed code. `/zeus:implement` normally reviews the diff before
handing off (and records the reviewed SHA); this is the **backstop** for when
`/zeus:create-pr` is invoked directly. It's a gate, not a fixer — create-pr never edits code.

```bash
REVIEWED=$(bash ${CLAUDE_SKILL_DIR}/scripts/journey.sh reviewed-sha 2>/dev/null || true)
HEAD_SHA=$(git rev-parse HEAD 2>/dev/null || true)
```

- If `$REVIEWED` == `$HEAD_SHA` → **skip** (this exact tree was already reviewed upstream by `/zeus:implement`).
- Otherwise (empty or stale) → **invoke `/zeus:review-pr` by name** (the skill, never its
  scripts — family doctrine). It auto-detects, and since the PR isn't open yet it reviews
  the **local working diff** and hands the findings back. Keep a short summary of the
  Confirmed findings (and notable Hypotheses) to show in the confirm step (2c).
- If `/zeus:review-pr` isn't installed → **skip silently** (independence preserved, same
  as the journey lookups above being no-ops).

create-pr does **not** fix anything here. If findings warrant changes, the user picks
"Fix first" at the confirm step and control returns to the LLM (or `/zeus:implement`) to
fix them normally; re-run `/zeus:create-pr` afterward.

### 2. Generate title + body

#### Title
- Format: `type(scope): description`
- Examples: `feat(web): add unified search`, `fix(scanner): resolve timeout in LLM calls`

#### Body — JSON state → renderer

The body is rendered deterministically from a state JSON. The agent fills field values; the renderer enforces layout, managed-block delimiters, and `Closes #N` placement. This eliminates template drift across runs.

1. Initialize a state skeleton:
   ```bash
   bash ${CLAUDE_SKILL_DIR}/scripts/init-state.sh \
     ${ISSUE_NUMBER:+--with-issue "$ISSUE_NUMBER"} > "$STATE_FILE"
   ```
   Required fields the agent must fill: `purpose`, `scope`, `what_this_does`, `rollback`. Recommended: `non_goals`, `outcome`, `key_changes`, `test_plan.acceptance`, `risks`. Optional/human-owned: `design_decisions`, `deliberately_excluded`, `logic`, `pre_merge_checks`.

   For `test_plan.manually_verified`, fill the object shape `{summary, evidence: [...]}`. `summary` is the one-line claim a reviewer reads at a glance ("traced a real multi-GDS case end to end"). `evidence` is a list of **verbatim** markdown blocks rendered as-is inside a collapsible `<details>` — paste the real command and its output in a fenced code block, a `mermaid` trace of the path exercised, or a before/after table: whatever lets a reviewer *independently confirm* the claim is true, not a paraphrase of it. Redact secrets from pasted output and keep it to the decisive artifacts, not full logs. A bare string is still accepted (rendered inline, no `<details>`). If a `verify`-style skill is installed it can produce this evidence for you — see `references/test-evidence-contract.md` for the full shape and the optional handoff.

2. **Issue-linked seeds (optional)** — when `$ISSUE_NUMBER` is non-empty, prefill values from the issue
   (the helper prefers `/zeus:propose`'s persisted state JSON when the issue was authored in this
   worktree — a stable key contract — and falls back to parsing the rendered body otherwise):
   ```bash
   # Original Intent (Purpose ← Context, Scope ← Proposal, Non-goals ← What's Excluded)
   bash ${CLAUDE_SKILL_DIR}/scripts/seed-from-issue.sh original-intent "$ISSUE_NUMBER"
   # Acceptance criteria (lifts ## Verification / Acceptance as bare criterion lines → test_plan.acceptance)
   bash ${CLAUDE_SKILL_DIR}/scripts/seed-from-issue.sh test-plan "$ISSUE_NUMBER"
   # Design Decisions (only resolved Default leans without [draft] tag)
   bash ${CLAUDE_SKILL_DIR}/scripts/seed-from-issue.sh design-decisions "$ISSUE_NUMBER"
   ```
   The agent reads these outputs and writes them into the corresponding state fields via `jq` or Edit (e.g. the `test-plan` lines become `test_plan.acceptance` string items — one criterion per element, no `- [ ]` prefix).

3. Render:
   ```bash
   bash ${CLAUDE_SKILL_DIR}/scripts/render-body.sh "$STATE_FILE" > "$BODY_FILE"
   ```

#### Field guidance (what the agent fills)

**Array item shapes** (the renderer indexes these keys per element — a bare string where an object is expected aborts the render):

- `outcome` — array of **strings**
- `test_plan.acceptance` — array of **strings** (each a criterion)
- `key_changes` — `{area, why}`
- `test_plan.not_tested` — `{gap, why_not, mitigation}`
- `risks` — `{risk, real, mitigation}`
- `design_decisions` — `{title, body}`
- `deliberately_excluded` — `{item, why}`

- **`purpose` / `scope`** — durable, human-readable scope context.
- **`what_this_does`** — 2-4 sentences of behavior framing in present tense. Concrete; don't restate the title.
- **`outcome`** — observable bullets. Include at least one on what is deliberately NOT changing — scope boundaries help triage.
- **`key_changes`** — keyed by area (folder / layer / subsystem), not a raw file list.
- **`test_plan.acceptance`** — acceptance criteria a reviewer ticks off; seeded from the linked issue's Verification/Acceptance section, or filled manually. Not for CI commands — automated test results come from GitHub Actions status checks (see the No-GitHub-duplication constraint).
- **`test_plan.not_tested`** — gaps + mitigation table; the highest-signal section, so populate it whenever a reviewer might catch a gap.
- **`pre_merge_checks`** — SQL probes / drain queries / feature-flag flips a reviewer runs before merge (distinct from a deploy sequence). Blank when none.
- **`rollback`** — one sentence on how to revert safely. Almost every PR can answer this; blank only when truly trivial.
- **`design_decisions`** — numbered trade-offs and non-obvious choices. Only when there's a decision worth surfacing.
- **`deliberately_excluded`** — grows during review as reviewers ask "why not X?".
- **`closes_issue`** — when set, the renderer appends `Closes #<N>` so merging auto-closes the linked issue.

Don't fill any field with what GitHub already shows (base branch, commit structure, file lists, code references); see Constraints. `design_decisions` and `deliberately_excluded` are human-owned — refresh never rewrites them.

### 2b. Validate the body (fail-fast guard)

Before showing the preview, write the composed body to a draft file and run:

```bash
bash ${CLAUDE_SKILL_DIR}/scripts/validate-pr.sh "$BODY_FILE"
```

Required sections: `## Original Intent` (with at least `- Purpose:` and `- Scope:`), `## What this does`, `## Test Plan`, `## Rollback`. Exit non-zero ⇒ fix the gap before continuing. Soft warnings (missing managed block, missing Non-goals, linked-issue body has no `Closes #N`) are printed but don't block.

### 2c. Confirm with the user

**Preferred (Claude Code):** call AskUserQuestion with a one-screen preview. Generate the preview deterministically:

```bash
bash ${CLAUDE_SKILL_DIR}/scripts/preview.sh "<title>" "$BODY_FILE" 60
```

If the backstop review (1c) produced findings, show a one-line-per-finding summary
above the preview so the decision is informed, and offer the **Fix first** option.

Options:

- **Post as-is** — runs step 3.
- **Fix first** — *(offer only when 1c surfaced findings)* stop without posting and
  hand control back to the LLM (or `/zeus:implement`) to fix the findings normally;
  re-run `/zeus:create-pr` afterward. create-pr does not fix code itself.
- **Edit** — open the draft for inline edits, then re-ask.
- **Save draft only** — print `$BODY_FILE` and stop.
- **Cancel** — discard.

**Fallback (other agents):** if AskUserQuestion isn't available, pipe `preview.sh` to stdout, then prompt via bash:

```bash
bash ${CLAUDE_SKILL_DIR}/scripts/preview.sh "<title>" "$BODY_FILE" 60
read -r -p "[1] Post  [2] Edit  [3] Save only  [4] Cancel > " choice
```

### 3. Create mode

If the user is creating a PR:

1. The validate + preview gate above must have passed.
2. After confirmation, post via the wrapper (handles `gh pr create` + best-effort journey write in one call):
   ```bash
   bash ${CLAUDE_SKILL_DIR}/scripts/post-pr.sh \
     --title "<title>" --body-file "$BODY_FILE" \
     [--base <branch>] [--label <l>] [--reviewer <u>]
   ```
   **Create PRs ready for review by default — never pass `--draft` unless the user explicitly asks for a
   draft** (e.g. "open a draft PR", "draft only", "not ready yet"). Omitting the flag makes `gh pr create`
   open a ready PR, which is what triggers reviewers and the `/zeus:address-pr` → `request-review` handoff.
3. The wrapper prints the PR URL on success and (best-effort) persists `pr.number` / `pr.url` to `journey.json` for downstream skills (`/zeus:address-pr`).
4. The wrapper appends a best-effort Claude Code session-usage footer via `telemetry.sh --pr` (vendored identically with `/zeus:propose`; self-disabling outside Claude Code or when `CLAUDE_PR_TELEMETRY=0`). See that script's header for the cost/marker details.

### 4. Refresh mode

If the user asks to refresh/update the PR body after later pushes, or invokes `/zeus:create-pr refresh`:

1. Prepare — `refresh.sh prepare` identifies the PR, writes the current body to a tmp file, and reports whether a managed block exists:
   ```bash
   PREP=$(bash ${CLAUDE_SKILL_DIR}/scripts/refresh.sh prepare [<PR_NUMBER|URL|BRANCH>])
   ```
   Read `$PREP`'s `.action`:
   - `noop` — nothing to refresh (no PR found, or body has no managed block). Stop with the printed reason.
   - `prepared` — proceed.
2. Regenerate **only** the machine-owned block from current branch truth and write it to a file (e.g. `/tmp/refresh-managed-new.md`). Use `render-body.sh managed-only` if you're driving the JSON state pipeline (recommended), or write the block by hand. This is the only step that requires agent judgment.
3. Apply — splice + diff + push in one call:
   ```bash
   bash ${CLAUDE_SKILL_DIR}/scripts/refresh.sh apply \
     "$(echo "$PREP" | jq -r .body_file)" \
     /tmp/refresh-managed-new.md \
     --pr-number "$(echo "$PREP" | jq -r .pr_number)"
   ```
   Returns `{action: "noop", reason: "managed block unchanged"}` when the regeneration produced an identical block, or `{action: "edited", pr_number, body_file}` when `gh pr edit` was called.

### 5. Constraints
- **Human-first:** Keep the body useful to reviewers; do not turn it into a metadata store.
- **Low-churn:** Refresh only the managed block; never auto-rewrite `Original Intent`, `Design Decisions`, or `What's deliberately excluded`.
- **Deterministic where possible:** derive refresh content from live branch/PR state.
- **Preserve human edits:** anything outside the managed block belongs to the human.
- **No GitHub duplication:** if GitHub or `gh api` already provides it directly, do not put it in the PR body by default.
- **Trade-off transparency:** surface "what's deliberately excluded" up front rather than leaving reviewers to ask. The skill provides the slot; the author fills it.
